# 핫스팟 군집 3D 인벨롭 — 결정과 근거

## 2026-09-13 착수 — 조사에서 확인한 사실

### 생각보다 많이 되어 있었다
deep report 핫스팟 탭의 3D 뷰가 이미 구 인벨롭·값 색칠·문자 라벨·회전을 한다
(`html_report.py:2386-2415`). 군집 데이터도 `center`·`radius_enclosing`·
`stress_max/mean`·`strain_max/mean`·`volume` 를 갖는다. 새로 만들 것은
**메쉬 · 전각도 집계 · 각도 라벨 · 컨투어 · 리스크 척도 · 오프라인화** 여섯이다.

### 군집은 deep report 전용이다
`hotspot_clusters` 를 읽는 파이썬은 `koo_deep_report` 뿐이다.
`koo_sphere_report` 에는 전혀 없다 (grep 결과 hotspot 은 CSS 클래스명과
무관한 elemFreq 용어뿐). 전각도로 가져오려면 로더에 수집 경로를 새로 만들어야 한다.

### 전각도 캠페인에 아직 군집 데이터가 없다
`Test_006_Fibonacci_6deg`·`Test_001_Full26_1Step` 모두 `hotspot_clusters` 없음.
군집 기능이 나중에 생겨서다. **각도별 군집을 보려면 해석을 다시 돌려야 한다.**
이건 사용자 판단 영역(시간·라이선스)이라 계획에 전제로만 적는다.

## 왜 자체 캔버스를 기본으로 두는가
sphere 리포트는 **외부 스크립트를 하나도 안 쓴다** (grep 으로 확인, CDN 참조 0).
deep report 만 `cdn.plot.ly` 를 쓴다. 전각도에 Plotly CDN 을 들이면 폐쇄망에서
3D 뷰가 조용히 죽는다 — 이 저장소가 싫어하는 무음 실패다.
메쉬 렌더는 `drawDeviceMesh` 로 이미 있으니 회전만 붙이면 되어 비용도 낮다.
Plotly 는 **번들 옵션**으로 제공하고, deep report 도 같은 번들로 오프라인화한다.
Plotly 2.27.0 = 3.60 MB (실측). deep report 866KB → 약 4.5MB 가 된다.

## 파괴 에너지 — 정직하게 근사임을 밝힌다
사용자 의도는 타당하다. 짧은 응력 스파이크보다 에너지가 손상을 더 잘 대변한다.

그러나 **참 파괴에너지는 지금 데이터로 못 낸다.** `HotspotClusterAnalyzer` 는
요소별 **극값·그 시각·그 시점의 짝 변형률**만 받는다
(`HotspotClusterAnalyzer.hpp:338-352` 의 `elem_max` / `elem_max_time` / `elem_strain`).
시간 이력이 없으므로 `∫σ dε` 를 만들 수 없다.

쓸 수 있는 것은 `σ̄ · ε̄ · V` — **피크 순간**의 변형에너지밀도 × 부피다.
응력만 보는 것보다는 낫다(응력이 튀어도 변형이 없으면 작게 나온다). 하지만
적분값이 아니므로 화면에 **"에너지 근사(피크 순간)"** 로 표기해 오해를 막는다.

참값을 원하면 `SinglePassAnalyzer` 가 상태를 훑으며 요소별 `∫σ dε` 를 누적하는
경로를 새로 만들어야 한다 — 별건으로 제안한다.

## 군집 criterion 은 응력 3종뿐
`HotspotCriterion` = `VonMises` / `MaxPrincipal` / `MinPrincipal`
(`HotspotClusterAnalyzer.hpp:28-32`). 변형률·에너지로 **군집화**하려면 C++ 열거형과
파서 확장이 필요하다. 다만 **색칠 기준량**은 군집에 이미 `strain_*` 가 실려 있어
파이썬만으로 바꿀 수 있다. 그래서 1단계는 색만, 2단계는 군집화까지로 나눈다.

## 각도 이름 표기
사용자가 "V1~8" 이라 했으나 이 저장소 규약은 **C1~C8**(코너)이다
(`AngleSourceParser.CUBOID_CORNERS`). 같은 것으로 보고 C 로 통일한다.
면 F1~F6, 모서리 E01~E12 와 합쳐 26방향.

## 있을 때 / 없을 때
바로 앞 작업(PR #2)에서 세운 규율을 그대로 따른다.
- 값이 없으면 **키 자체를 안 넣는다** (0/null 로 안 채움)
- 화면에서는 **선택지에서 감춘다** (빈 차트로 '값 0' 오독 방지)
- `strain_available=false` 인 데이터셋에서는 변형률·에너지 척도를 감춘다


## 2026-09-13 — 참에너지 적분으로 결정 (사용자: "참에너지 적분이지 당연히")

근사(`σ̄·ε̄·V`)를 버리고 **시간 적분**을 구현한다. 조사 결과 가능하다.

### 무엇을 적분하는가 — 소성일 밀도

```
w_p = ∫ σ_vm dε_p        [MPa = mJ/mm³ (ton-mm-s)]
군집 에너지 = Σ_e w_p,e · V_e   [mJ]
```

**왜 총변형일(∫σ:dε)이 아니라 소성일인가.**
사용자 의도가 "짧게 튄 응력보다 실제 손상" 이다. 소성변형률 ε_p 는 단조증가라
**탄성 스파이크는 Δε_p = 0 이라 기여가 0** 이다. 정확히 의도대로 걸러진다.
총변형일은 탄성 왕복분까지 더해 스파이크를 다시 세게 만든다.

**결정적 이점 — STRFLG 가 필요 없다.**
`extractEffPlasticStrain` 은 솔리드 word 6 을 바로 읽는다
(`SinglePassAnalyzer.cpp:1255-1263`). 변형률 텐서(STRFLG) 경로와 달리
**거의 모든 덱에서 나온다.** 주변형률·ε_vm 이 없는 캠페인에서도 에너지는 나온다.

### 어디에 넣는가

`accumulateElementExtremes` 의 요소별 루프가 이미
- 상태 `si` 를 돌며
- `sd[base+0..5]` 로 응력 텐서를,
- `sd[base+6]` 으로 ε_p 를

읽는다 (`SinglePassAnalyzer.cpp:1393-1460`). **같은 루프에서 누적하면 추가 I/O 가 0.**
병렬화 축이 요소라 각 스레드가 자기 요소만 쓰므로 경쟁도 없다.

### 적분 규칙
- 사다리꼴 — `w += 0.5·(σ_i + σ_{i−1})·(ε_i − ε_{i−1})`
- **`Δε_p < 0` 은 버린다.** 소성변형률은 단조증가라 음수 증분은 수치잡음/언로딩
  아티팩트다. 누적하면 에너지가 줄어드는 비물리가 된다
- 상태가 1개뿐이면 적분 불가 → 미기록(NaN)으로 둔다. 0 으로 채우면
  '에너지 0' 과 '계산 못 함' 이 구분되지 않는다

### 군집까지 어떻게 전달하는가
`computeHotspotClusters` 가 이미 `elem_strain` 을 **요소별 병렬 배열**로 받는다
(`HotspotClusterAnalyzer.hpp:349-354`, `ElementExtremes.strain`).
`elem_energy` 를 같은 패턴으로 하나 더 붙인다. 요소 부피는 군집기가 이미
계산하므로(`cluster.volume`) 총합 `Σ w·V` 를 거기서 만든다.

### 군집 출력에 더할 필드
- `energy_total` — 군집 총 소성일 [mJ] (리스크 맵 가중치의 1순위)
- `energy_max` · `energy_mean` — 요소별 밀도의 극값·부피가중 평균 [mJ/mm³]
- `energy_available` — 적분 못 한 덱에서 false (허구 0 금지)

### 범위
군집 **기준량(criterion)** 을 에너지로 바꾸는 것은 여전히 2단계로 둔다.
1단계는 기존 응력 기준으로 잡은 군집에 **에너지 값을 실어** 색·컨투어 가중에 쓴다.


## 2026-09-13 구현·검증 — 적분 규칙을 '음수 버림' 에서 '러닝맥스' 로 바꿨다

작은 캠페인(`/data/battery_study/case_01_phase1_stacked_tier-1`, 22상태·솔리드 1,161요소)
으로 검증하다가 **처음 정한 규칙이 틀렸다는 것을 실측으로 발견**했다.

### 실측 — ε_p 가 단조증가하지 않는다
| 항목 | 값 |
|---|---|
| Δε_p 양수 전이 | 9,267 |
| **Δε_p 음수 전이** | **10,470 (42.9%)** |
| ε_p 이력 최댓값 | 8.68913e-06 |
| **ε_p 최종값** | **1.28766e-07** (최댓값의 1/67) |

참 유효소성변형률은 **감소할 수 없다.** word 6 을 다른 이력변수로 쓰는 재료이거나
요소 소거 등이 원인으로 보인다.

### 세 규칙 비교 (최대 w_p)
| 규칙 | 값 | 문제 |
|---|---|---|
| A 음수 버림 | 1.295e-05 | 오르내림을 **정류(rectify)** 해 잡음을 누적 |
| B 그대로 | 8.52e-07 | 에너지가 감소하는 비물리 |
| **C 러닝맥스 초과분** | **1.29499e-05** | 오르내림을 몇 번 반복해도 중복 없음 |

이 덱은 '한 번 크게 올랐다가 내려오는' 모양이라 A 와 C 가 우연히 거의 같다.
그러나 **오르내림이 반복되는 덱에서는 A 가 몇 배로 부풀려진다.** C 를 택했다.

상한 점검 — `σ_max·ε_p,max = 2.59218e-05` 이고 A·C 모두 그 **50.0%** 다.
0→peak 삼각형 적분(½σε)과 정확히 일치해 적분이 물리적으로 타당함을 뒷받침한다.

### 무음 금지 — 경고를 붙였다
ε_p 감소 전이가 10% 를 넘으면 한 줄 알린다. 조용히 넘어가면 잡음 누적분을
실제 손상으로 오독한다.
```
[hotspot] 소성일: ε_p 가 감소한 전이가 42.9433% — word 6 이 유효소성변형률이
아닐 수 있습니다. 누적은 이력 최댓값 초과분만 더합니다.
```

### 독립 검증
분석기와 **별개 코드 경로**로 d3plot 을 직접 읽어 적분하는 프로그램을 만들어 대조했다.
- 독립 계산 최대 w_p = **1.29499e-05** = 분석기 `energy_max` **1.295e-05** ✅
- 내부 일관성 `energy_mean × volume == energy_total` ✅
- 기존 필드(stress/radius/volume/element_count) 회귀 **0건** (공통 군집 40개 전수 대조)

### 셸·두꺼운 셸
적분점(층) 평균 σ_vm·ε_p 로 두께 방향을 대표시킨다. ε_p 는 층 블록의
응력 6워드 다음(`ioshl_[1]`)에 있다. 솔리드와 같은 러닝맥스 규칙.
`weight_measure` 가 `area`(두께 없는 셸)면 `energy_total` 이 에너지 단위가
아니므로 내지 않고 밀도만 낸다.

## G5b — 색 척도 선택 (2026-09-13)

**결정 1: 균일값은 최고위험 색으로 칠하지 않는다.**
기존 `tOf` 는 `vmax === vmin` 일 때 `t = 1` 을 줬다. 응력에서는 "균일하게 높다" 가
사실일 수 있지만, 소성일에서는 탄성 거동 파트가 전부 0 인데 가장 진한 빨강이 된다.
실덱 파트 13(thick_shell)이 정확히 그 경우였다. 균일이면 중립 회색 + 컬러바 숨김 +
"이 파트는 소성 변형이 없습니다 (탄성 거동)" 주석으로 바꿨다. 0 을 위험으로 보이게
하는 것은 허구 값 표시와 같은 종류의 거짓말이다.

**결정 2: 툴팁에 선택한 척도 값을 함께 적는다.**
컬러바는 "소성일" 인데 툴팁은 응력 숫자만 보여 줬다. 색과 숫자가 어긋난 채로 읽히면
독자가 응력을 에너지로 오인한다. 응력이 아닌 척도를 고르면 그 값을 한 줄 더 붙인다.

**결정 3: 소성일 전용 포매터.**
공용 `fmt`(소수 2자리)로는 `energy_max` 2.061e-3 이 `0.00` 이 되어 "값 없음" 과
구분되지 않는다. |v| < 0.01 이면 지수 표기(유효 3자리)로 찍는다.

**부수 수정: 3D→2D 빠른 전환 시 JS 예외.**
`hsDraw3D` 의 `Plotly.newPlot(...).then()` 이 카메라를 맞추려고
`el.layout.scene.aspectratio` 를 읽는데, 그 사이 2D 로 다시 그려지면 `scene` 이
없어 `TypeError` 가 난다. 기존 결함이며 `if (!el.layout || !el.layout.scene) return;`
한 줄로 막았다.

**가용성 필터 검증의 한계 (정직하게 기록).**
검증 덱(case_01_phase1_stacked_tier-1)은 군집이 있는 21개 항목 전부
`energy_available = true` 였다. 즉 "없으면 감춘다" 분기를 실데이터로 밟을 수 없었다.
브라우저에서 군집 사본의 에너지/변형률 필드를 지워 확인했다 — 선택지에서 사라지고,
상태에 남은 감춰진 척도는 2D·3D 모두 응력으로 폴백한다. 실데이터 확인은 에너지가
없는 덱(STRFLG 미설정 등)이 생기면 다시 해야 한다.

## G0 — sphere 가 군집을 받는 경로 (2026-09-13)

**빈 군집 항목은 버린다.**
`analysis_result.json` 의 `hotspot_clusters` 는 파트 × 기준량 × 요소종류로 항목이
생기는데, 실제 군집이 하나도 안 잡힌 항목도 껍데기로 남는다. 미니 캠페인에서 런당
23항목 중 군집이 있는 건 6~7개뿐이었다. 껍데기를 그대로 넘기면 리포트가 "군집 있음"
으로 판단해 빈 그림을 그린다. `clusters` 가 비면 수집 단계에서 버린다.

**없으면 키 자체를 만들지 않는다.**
`report.json` 의 런 요약에 `hotspot_clusters` 를 빈 배열로라도 넣으면, 읽는 쪽이
"핫스팟을 돌렸는데 아무것도 안 나왔다" 와 "애초에 안 돌렸다" 를 구분할 수 없다.
군집이 있을 때만 키를 만든다.

**왜 안 나오는지는 로더만 말할 수 있다.**
탭이 비었을 때 원인은 두 가지다 — (1) `--hotspot-clusters` 없이 분석했다,
(2) `--hotspot-part` 로 좁힌 파트에 군집이 없다. 리포트 HTML 은 둘을 구분할 정보가
없으므로 `load_all` 이 그 자리에서 각각 다른 문구로 알린다.

**검증 캠페인 (작게 먼저).**
`/data/Tests/Test_001_Full26_1Step` 의 26각도 중 자세가 서로 다른 4각도를 골라
심볼릭 링크 팜으로 미니 캠페인을 만들고, 로컬 빌드 `unified_analyzer` 로
`hotspot_clusters.enabled: true` 를 켜 재분석했다 (4런 모두 성공, 군집 31~42개).
원본 26각도 전체를 다시 돌리는 건 output 이 92GB 라 이 단계에서는 불필요하다.

**모델은 회전하지 않는다. 회전하는 것은 낙하 속도 벡터다.** 그래서 각도가 달라도
모든 런의 d3plot 형상은 같은 기기(body) 좌표계이고, 그것이 시나리오 원본 `.k` 의
좌표계다. 전각도 군집을 파트 메쉬 하나에 그대로 얹을 수 있다.

방향도 `impactDirBody`(Rᵀ·(0,0,-1), `html_report.py:1264`)와 정확히 맞는다 —
pitch 90 → (1,0,0), pitch 45 → (0.7071,0,−0.7071), 덱 속도와 일치.

군집 `center` 는 **초기 형상 기준**이다 (`HotspotClusterAnalyzer.hpp:157`
"응력×부피 가중 중심 (초기 형상 기준)"). 변형 후 좌표가 아니므로 make_stl 이
원본 `.k` 에서 뽑은 메쉬와 바로 겹친다.

**만약 반대였다면** 각도마다 Rᵀ 로 되돌려야 했고, 그 변환을 빠뜨리면 군집이
엉뚱한 면에 찍히면서도 그림은 멀쩡해 보였을 것이다. 그래서 먼저 확인했다.

## G1 정정 — 회전은 같았지만 **평행이동이 달랐다** (2026-10-17)

위 절의 결론("변환이 필요 없다")은 **틀렸다.** 회전만 보고 이동을 안 봤다.
두 런의 `*NODE` 를 비교했는데 둘 다 낙하 덱이라 공통 이동량이 보이지 않았다.

실측 — 미니 캠페인(Test_001 4각도)에서

| | x | y | z |
|---|---|---|---|
| 원본 `MinimumModel.k` 메시 bbox | 0.99 ~ 71.00 | 0.96 ~ 147.00 | 0.00 ~ 9.00 |
| 군집 중심 bbox | −34.48 ~ 35.08 | −72.45 ~ 72.93 | −4.15 ~ 3.75 |

**크기는 같고 원점만 다르다.** 낙하 덱이 모델을 원점 중심으로 옮긴다.
원본 `.k` 로 메시를 뽑으면 군집 104개 중 **90개가 메시 밖**에 찍힌다.

이 결함의 성질이 고약하다 — **그림은 멀쩡해 보인다.** 메시도 구도 색도 다 나오고
위치만 틀리다. 눈으로는 "핫스팟이 저기 있구나" 로 읽힌다.

**결정 1 — 형상 소스를 런의 d3plot 으로 바꿨다.** 군집이 나온 바로 그 형상에서
뽑으면 좌표계가 정의상 같다. 원본 `.k` 폴백은 **두지 않았다** — 폴백이 곧
틀린 좌표계이기 때문이다. d3plot 이 없으면 메시를 만들지 않고 사유를 말한다.

**결정 2 — 런타임 가드를 넣었다** (`_hotspot_frame_check`). 군집 중심의 절반
넘게가 메시 bbox 밖(여유 = 최대변의 2%)이면 **메시를 싣지 않고** 사유를 낸다.
틀린 그림보다 없는 그림이 낫다. 수정 전 메시로 돌려 90/104 를 실제로 잡는 것을
확인했다 (합성 데이터 시험 + 실데이터 재현 둘 다).

**파트가 메시에서 빠지는 사유는 단정하지 않는다.** 실측으로 세 갈래가 다 나왔다 —
(1) 모델에 없음(파트 23 = 덱에만 있는 바닥 플레이트, 원본 `.k` 에는 22파트),
(2) 다른 파트 안에 가려 외피에 안 나옴, (3) 선택 전체의 bbox 가 커서 복셀 격자가
얇은 파트를 삼킴(파트 15 는 두께 0.4 — 바닥까지 고르면 사라진다).
주석은 세 가능성을 적고 `--hotspot-part` 로 좁히라고 안내한다.

**바닥 플레이트는 기본에서 제외하지 않았다.** 파트 23 에 실제로 군집이 있다.
군집이 있는 파트를 조용히 빼는 것은 이 저장소가 거부하는 무음 결정이다.
대신 메시가 300×300 으로 커져 얇은 파트가 사라지는 것을 주석으로 알린다.
