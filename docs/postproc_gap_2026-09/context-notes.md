## 2026-09-13 — 우선순위를 갭 문서와 다르게 잡은 이유

갭 문서는 "물리적으로 틀렸던 건 전부 A 구간" 이라며 A 를 1순위로 뒀다. 그러나
**철회까지 간 잘못된 보고 2건은 전부 B-3·B-4** 에서 나왔다.

- B-3: 미완주 과제가 섞여 공통 DOE 185→27, "T4 ×1.97~2.49" 보고 후 철회
  (올바른 값 ×2.66~4.02)
- B-4: 귀무를 `(N+1)/(k+1)` 로 잘못 골라 "랜덤 수준" 결론 → `(N+1)/2` 로 고치니
  F1_Back p=0.016 으로 뒤집힘

A 구간 오류(min_principal 을 항복과 직접 비교)는 작성자가 스스로 잡았다. B 구간은
보고된 뒤에 잡혔다. 그리고 B-3·B-4 는 교집합 계산과 통계 유틸이라 A-3 보다 싸다.
"피해 크기 ÷ 구현 비용" 으로 재배치했다.

## 2026-09-13 — P0-1 구현 중 검증기가 스스로 거짓말할 뻔했다

`verify_package.sh` 첫 판이 v29(정상 아카이브)에서도 `bin/unified_analyzer` 가
없다고 했다. 원인은 이것이다.

```bash
set -uo pipefail
echo "$listing" | grep -qxF "$path"    # ← 이게 문제
```

`grep -q` 는 첫 매치에서 **즉시 종료**한다. 그러면 아직 쓰고 있던 `echo` 가
SIGPIPE 로 죽고, `pipefail` 이 파이프라인 종료 상태를 실패로 만든다. 결과적으로
**목록 앞쪽에 있는 항목일수록 "없다" 는 거짓 실패**가 났다. `env.sh` 는 목록
끝 근처라 통과하고 `bin/*` 은 앞쪽이라 실패하는, 재현은 되지만 이유를 모르면
납득이 안 되는 형태였다.

here-string(`grep -q ... <<< "$listing"`)으로 파이프를 없애 해결했다.

검증 도구가 거짓 실패를 내는 것은 거짓 통과보다는 낫지만, 몇 번 겪으면 사람이
검증을 꺼버린다 — 결국 같은 곳으로 간다. 검증기에는 **자기 자신에 대한 테스트**가
필요해서 합성 케이스 6종(정상 / unknown 버전 / VERSION 누락 / lib 누락 /
최상위 2개 / 손상 tar)을 만들어 통과시켰다.

## 2026-09-13 — 패키징에서 구조 변환은 하지 않기로

배포본은 `SmartTwinPostprocessor/{bin,lib,env.sh}` 이고 `build_module.sh` 산출물은
`{bin,python,lsprepost,activate.sh,VERSION}` 이다. 둘 사이 변환 절차는 리포지토리에

굳히는 것**이 된다.

그래서 `package_module.sh` 는 `--from-dir` 만 받는다. 이미 만들어진 배포 디렉토리를
그대로 묶고, VERSION 누락만 막는다. 추측이 0이면서 이번 사건은 100% 막힌다.
SIF→디렉토리 변환을 스크립트화하는 것은 별도 과제로 남긴다.

## 2026-09-13 — P1-1: 내가 만든 energy_total 도 같은 병이었다

갭 문서는 클러스터 `volume` 이 `top_percent` 종속이라 물리량이 아니라고 지적했다.
`want = floor(rank.size() × frac)` 이라 **요소 개수 비율**이기 때문이다.

2026-09-13 에 넣은 `energy_total`(Σw_p·V)도 클러스터 안에서만 합산하므로 똑같이
종속이었다. 그래서 파트 단위 절대량을 따로 만들었다 — 상위 백분위로 자르기 **전에**
파트 전체 요소로 집계한다. 클러스터 값은 "어디가 뜨거운가", 파트 절대량은
"얼마나 망가졌는가" 로 역할이 갈린다.

ε_p 는 마지막 프레임이 아니라 **이력 최댓값**을 쓴다. 갭 문서는 "시간 단조증가라
마지막 프레임만 읽으면 된다" 고 했지만, 소성일 작업에서 실덱의 ε_p 가 감소하는
전이를 이미 확인했다(42.9%). 단조를 가정하면 조용히 과소평가된다.

## 2026-09-13 — JSON 이 작은 값을 조용히 0 으로 만들고 있었다

독립 검증에서 `max_eps` 만 상대오차 1e-4 로 어긋났다. 계산이 아니라 **출력** 문제였다.

```cpp
oss << std::fixed << std::setprecision(8) << v;   // 소수점 이하 8자리 고정
```

`8.689126844e-06` → `0.00000869` (유효숫자 3자리). 더 작은 값은 `0.00000000` 이
되어 **진짜 0 과 구분되지 않는다.** 소성일 밀도가 1e-9 수준인 파트가 실제로 있으니
값이 조용히 사라지고 있었다.

`std::setprecision(10)` (defaultfloat)으로 바꿔 필요할 때 지수 표기가 나오게 했다.
지수 표기는 JSON 에서 유효한 숫자다. 고친 뒤 독립 검증 5/5 상대오차 0.

이건 내가 추가한 필드가 드러낸 **기존 결함**이다. 리포트 쪽은 `hsMetricFmt` 로
표시만 고쳐 뒀었는데, 데이터 자체가 잘리고 있었으면 표시를 고쳐도 소용없다.

## 2026-09-13 — P1-2: 셸 레이아웃을 추측했다가 50배 틀렸다

2패스에서 셸 계열 층 stride 를 이렇게 **추측**해서 썼다.

```cpp
const int P = 6*(ioshl_[0]?1:0) + (ioshl_[1]?1:0) + (ioshl_[2]?6:0) + (ioshl_[3]?1:0);
```

원본(`accumulateLayeredExtremes`)은 이렇다.

```cpp
const int P = 6 * ioshl_[0] + ioshl_[1] + neips_;
```

`neips_` 를 `ioshl_[2]/[3]` 로 잘못 대체해 stride 가 어긋났고, 엉뚱한 메모리를 읽어
`max_t(mean_e)` 가 `mean_e(max_t)` 의 **50배**로 나왔다. 수학적으로 불가능한 값이다.

이걸 잡은 것은 **부등식 검증** 덕분이다. `mean_e(max_t) ≥ max_t(mean_e)` 는 정의상
항상 참이므로, 위반이 나오면 반드시 구현이 틀린 것이다. 솔리드는 비율이 정확히
1.0000 으로 맞았고 셸 계열만 틀려서 범위도 바로 좁혀졌다.

교훈 — 이미 코드에 있는 레이아웃 공식은 **복사**해야지 다시 유도하면 안 된다.
그리고 물리적으로 반드시 성립하는 부등식이 있으면 그걸 검증에 쓰면 구현 오류가
숨지 못한다.

## 2026-09-13 — P1-3: 좌표계를 추측하지 않고 규격을 찾아봤다


**응력은 전역, 요소 좌표계는 합력(모멘트·전단력)에만** 해당한다. 우려가 근거

교훈 — 셸 stride 를 추측해서 50배 틀린 직후였기에 이번엔 규격을 먼저 찾았다.

## 2026-09-13 — P2: 시험 기준이 틀려서 멀쩡한 구현이 떨어졌다

평균순위 검정의 p 분포를 "난수 4000회의 십분위가 고른가" 로 시험했더니 실패했다.
구현을 의심하기 전에 전수 열거로 확인했다 — N=6, k=4 는 경우가 1296개뿐이라
**모든 경우를 셀 수 있다**.

```
가능한 p 값 21가지, P(p ≤ v) == v 위반 0건 (최대 오차 0.00e+00)
```

구현은 정확했다. 십분위 균일성은 p 값이 21가지뿐인 **이산** 분포에 쓸 수 없는
기준이었다(값이 없는 십분위가 생긴다). 시험을 "정확 검정이 만족해야 하는 성질"
로 바꿨다 — 표본추출보다 강하고 결정적이다.

교훈 — 시험이 실패하면 구현과 시험 **둘 다** 용의자다. 이번엔 시험이 범인이었고,
난수 대신 전수 열거로 바꾸니 의심의 여지가 없어졌다.

## 2026-09-13 — 갭 문서의 p=0.016 은 재현되지 않는다

문서는 "F1_Back 이 4과제 중 3개에서 1위, p=0.016" 이라 적었다. N=6, k=4 로
계산하면 나머지 한 과제가 3위면 p=0.0116, 4위면 p=0.0270 이다. **0.016 은
나오지 않는다.**

조건(면 수, 양측 여부, 다른 검정)을 모르므로 "재현됐다" 고 쓰지 않았다. 구현
정확성은 전수 열거로 따로 확정했다. 이 항목은 문서 작성자가 조건을 밝히면
다시 맞춰 볼 것.

## 2026-09-13 — "누가 교집합을 줄였나" 가 핵심이다

교집합이 185 → 27 로 준 사실 자체는 로그에 있었을 것이다. 그런데 아무도
알아채지 못했다. 숫자만으로는 **원인**이 안 보이기 때문이다.

그래서 케이스를 하나씩 빼 보고(leave-one-out) 교집합이 얼마나 회복되는지
계산해 범인을 지목한다.

```
공통 DOE 가 27개로 임계 50개 미만입니다 — 이 표본으로는 리비전 간 수치를
비교할 수 없습니다. 'T4_PV1' 를 빼면 185개가 되므로, 그 케이스가 아직 다
돌지 않았는지 확인하세요
```

이 한 줄이 있었으면 그날 틀린 수치를 보고하지 않았을 것이다.

## 2026-09-13 — 의존을 줄이는 것이 에러를 줄인다

통계 유틸은 numpy 조차 쓰지 않는다(import 는 방어적으로 감쌌다). scipy 는 SIF
안에 있지만 호스트 배포본에도 있다는 보장이 없고, 없으면 그 자체가 에러다.
순수 Python 으로 쓰면 어디서든 돈다 — 실제로 numpy 를 차단한 환경에서도
import·계산이 정상 동작함을 확인했다.

모든 함수는 **예외를 던지지 않는다.** 보고서 생성 중 예외가 나면 리포트 전체가
죽기 때문이다. 계산할 수 없으면 값은 `None` 이고 사유가 `note` 에 담긴다.
경계 입력 34종(18 + 16)을 시험으로 고정했다.
