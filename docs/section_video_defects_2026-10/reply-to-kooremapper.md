**상태** K-1~K-4 · P-1 수정·커밋 완료(로컬 main, 아직 push·배포 전). P-2~P-4 는 보류.

## 1. 한 줄

K-1 은 원인을 LS-PrePost 안에서 찾아 없앴고, K-2~K-4 는 이제 틀린 결과 대신 실패(rc 1·rc 3)로 끝납니다.
네 건 모두 ROADMAP 1-3·1-5·1-7 로 넉 달 열려 있던 항목이었습니다.

## 2. 결함별

### K-1 LS-PrePost 응력 0 프레임 — 원인 확정, 제거 (441cfbd)
- **원인.** LS-PrePost 4.12 는 상태마다 메모리를 잡다가 합이 내부 예산 `max_memory` 를 넘으면 그 뒤 상태에 메모리를
  주지 않고, 그 상태들을 「min=0, max=0, at node# 0」 으로 그립니다. 예산 기본값은 `0.8 × wxGetFreeMemory()` 인데
  정적 링크된 wxWidgets 3.0 이 /proc/meminfo 를 옛 형식으로 읽어 사실상 **시작 시점 MemFree + 초기화 안 된 값**입니다.
  페이지 캐시에 따라 출렁여 비결정이었고, 보고하신 「MemFree ~1 GB 와 상관, 반례 하나」 가 이것으로 설명됩니다.
  예산 초과는 단조라 「어느 프레임부터 끝까지」 모양이 됩니다. VmPeak 가 상한 아래였던 것도 맞습니다 — rlimit 이 아니라
  LS-PrePost 내부 예산 문제입니다.
- **재현.** `$HOME/LSTC/LS-PrePost4.12/lsppconf` 에 `max_physical_memory = 20M` 을 주면 매번 같은 모양이 나옵니다.
- **처방.** 작업자 HOME 의 lsppconf 에 `max_physical_memory = 1000G` 를 적어 예산 검사를 사실상 끕니다. 이는 기존의
  「운 좋은」 정상 런과 같은 동작입니다(운영 덱 RSS 4.5 GB). 진짜 메모리가 모자라면 LS-PrePost 는 abort(134)하고
  moov 없는 mp4 를 남기는데, 이것은 아래 둘로 잡습니다.
  - LS-PrePost 의 종료 코드를 그대로 냅니다. 예전 실행 명령은 마지막 `wait $XVFB_PID` 의 코드를 써서 abort 도 성공이었습니다.
  - 산출물 검사: 영상 존재·1 KB 이상·ffprobe 로 열리는지.
- **확인.** 운영 덱 `Run_20260602_093237_801e2b`, 12 GiB 상한, 운영 cfile 형식 그대로 → 4,952 프레임, 마지막 프레임
  max 131.131 at elem# 19378(그쪽 정상 영상과 같음). 미리 심은 20M 설정은 덮어써 정상, 1.6 GB 상한에서는 FAILED + rc 3.
- **넣지 않은 것.** 렌더 뒤 「0 프린지」 색 검사는 넣지 않았습니다. 0 프레임끼리도 모델 색이 다르고(B1 은 순청색, 재현은
  연청색) 정상 전체 모델 프레임도 98.6% 가 최저색이라 오탐·누락이 모두 납니다. 원인을 없앴고 남는 실패 경로(abort)는
  종료 코드로 잡히므로 재시도도 두지 않았습니다. `LSPP_STATE_MEMORY=off` 는 처방이 아닙니다(작은 예산과 함께면 여전히 0).

### K-2 상태 읽기 예외 삼킴 (66c9f7b)
- 파서는 예외(bad_alloc 포함)를 더 이상 삼키지 않습니다. 순차·병렬·상태 수 훑기가 같은 규칙으로 판정합니다.
  - 가족 파일 열기 실패 · 번호 구멍(예 d3plot05 없음, 06 있음) · 중간 파일이 상태 도중 끝남 → 실패.
  - 마지막 파일이 상태 도중 끝남 → 경고 후 앞 상태만(해석이 쓰다 끝난 덱 — Test_Cum26x3 이 실제로 그렇습니다).
- 「기대 상태 수」 는 파일 끝 모양으로 판정합니다. 운영 덱 249 가족 파일은 모두 상태 뒤 EOF 표지(-999999)로 끝나므로,
  중간 파일이 표지 없이 512 워드 이상 남기고 끝나면 잘림입니다. 한계: 상태 경계에서 정확히 잘린 중간 파일은 못 잡습니다.
- 운영 덱을 12 GiB 상한으로 분석하면 이제 20.8 초에 **rc 1 「상태 읽기 실패 — d3plot67: 메모리 부족(std::bad_alloc)」** 입니다.
  이 덱은 상태를 다 올리면 약 33 GB 라 이 상한으로는 원래 분석할 수 없습니다(스트리밍 분석은 별도 설계 과제).
  software 백엔드 단면 영상도 같은 읽기를 쓰므로 1,546 상태로 rc 0 이던 경우는 이제 실패입니다
  (분석과 함께 돌면 rc 1, `--render-only` 면 rc 3).

### K-3 스레드 상한 (66c9f7b, efd6c6c)
- 가족 파일마다 `std::async` 를 띄우던 것을 `num_threads`(기본 코어 수) 작업자 풀로 바꿨습니다. 스레드를 더 못 띄우면
  띄운 만큼(최소 호출 스레드)으로 계속합니다 — RLIMIT_NPROC=1 시험으로 확인. 첫 실패에서 남은 파일은 읽지 않습니다.

### K-4 렌더 실패 rc 0 (6a0d0d1)
- `unified_analyzer` 는 분석 결과는 썼지만 렌더 잡·파트 단면·단면 영상이 하나라도 실패하면 **rc 3** 입니다
  (재귀 모드 포함, 우선순위 1 > 3 > 2). `--help` 에 적었습니다.
- `koo_deep_report` 는 rc 3 을 분석 성공으로 보고 실패 줄을 `D3plotResult.render_warnings` 에 남기며, 2차 패스 실패도 남깁니다.
  보고서 렌더 갤러리에 경고 상자로 보입니다.
- **그쪽에 영향.** `unified_analyzer` 를 직접 부르면 rc 3 을 「분석 성공·렌더 실패」 로 다뤄 주십시오.

## 3. 개선 제안
- **P-1 개관 중복 — 반영 (c65bf31).** 파트별 2차 패스가 개관 영상을 다시 만들지 않습니다. 단면 영상 경로뿐 아니라 옛
  LS-PrePost 렌더 경로도 같은 중복이 있어 둘 다 고쳤습니다. 각도당 세션 144 → 141.
- **P-2 세션 수 · P-3 state_step · P-4 한 세션 여러 단면 — 보류.** 운영 기본값과 렌더 설계를 바꾸는 일이라 저희 사용자
  판단을 받은 뒤 하겠습니다. 참고로 K-1 처방 뒤 LS-PrePost 는 세션 안에서 상태를 다 메모리에 올리므로(운영 덱 4.5 GB),
  P-4 로 세션을 합치면 18 GB 다시 읽기를 줄이는 효과가 HDD 에서 특히 큽니다.

## 4. 여쭈신 것 (원문 §5)
1. **K-1 재현** — 네. 비결정 판은 다시 돌리지 않았고, 원인을 짚은 뒤 예산을 작게 강제해 결정적으로 재현했습니다(위 2절).
2. **이미 나간 운영 영상 일괄 점검** — 가능합니다. 예산 초과는 단조라 결함 영상은 **마지막 프레임이 반드시 0** 입니다.
   단면·개관 영상(자동 범위)은 마지막 프레임 범례 숫자가 모두 같은지로 가릴 수 있습니다. 다만 범위 고정 영상은 범례로
   안 갈리고, 색으로 가르는 것은 위 이유로 믿기 어렵습니다. 대상(어느 캠페인·노드의 영상인지)과 범위를 저희 사용자가
   정한 뒤 진행하겠습니다. 의심 영상은 새 이미지로 다시 그리는 것이 가장 확실합니다.
